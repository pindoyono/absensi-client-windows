# ADR-001: Offline-First Architecture

## Status

Accepted

## Context

The kiosk operates in a school environment where network reliability is unpredictable. Internet outages, bandwidth limitations, and server maintenance windows are common.

## Decision

Adopt an **offline-first** architecture where all critical operations (face capture, liveness check, attendance recording) work without network connectivity. Data is stored locally in an encrypted SQLite database (SQLCipher) and synced to the server when connectivity is restored.

## Consequences

- **Positive:** Zero downtime during network outages, no data loss, consistent user experience.
- **Negative:** Increased complexity in sync logic, potential for data conflicts, larger local storage requirements.
- **Mitigation:** Implement idempotent sync with server-side deduplication using client-generated UUIDs.

# ADR-002: MiniFASNet + ArcFace Model Selection

## Status

Accepted

## Context

Face recognition requires both liveness detection (anti-spoofing) and accurate face matching. Multiple model combinations were evaluated.

## Decision

Use **MiniFASNetV2** for liveness detection and **ArcFace (InsightFace)** for face embedding generation.

## Rationale

- MiniFASNetV2: Lightweight (mobile-friendly), high accuracy on spoofing detection, ONNX-compatible.
- ArcFace: Industry-standard face recognition model, 512-dim embeddings, excellent discrimination.

## Alternatives Considered

- OpenCV Haar cascades: Too slow, high false positive rate.
- MediaPipe: Good but requires internet for some features.

# ADR-003: SQLCipher for Local Database

## Status

Accepted

## Context

Attendance data is sensitive (student records). Local storage must be encrypted to prevent unauthorized access if device is stolen.

## Decision

Use **SQLCipher** (encrypted SQLite) for all local data storage.

## Rationale

- Transparent encryption at rest.
- Same SQL interface as SQLite — no code changes needed.
- Encryption key stored in Windows Credential Manager (not in .env).

# ADR-004: JWT + API Key Authentication

## Status

Superseded by Option B (see PRD-perbaikan-client-sesuai-server.md)

## Context

Device needs to authenticate to server for sync operations. Two types of access are needed:

1. Device-level access (sync attendance, pull embeddings).
2. Guru-level access (pull jadwal efektif, dispensasi).

## Decision

Use **dual authentication**:

- **Device API Key** for device-level operations (sync, embeddings).
- **Service JWT** for guru-level operations (jadwal, dispensasi).

## Rationale

- API key is simple, stateless, and sufficient for device identity.
- JWT allows fine-grained access control and expiration for guru-level operations.
- JWT auto-refresh mechanism implemented (REQ-CRED-001).

## Supersedence

Server endpoint `/auth/refresh-service-jwt` does not exist on live server.
Client JWT refresh chain is broken — silent 12h expiry causes stale jadwal/dispensasi cache.

**Option B implemented**: `/jadwal/efektif` and `/dispensasi/aktif` now accept Device API Key
via `get_guru_or_device` dependency. Service JWT removed entirely from client.
No JWT refresh needed — device API key is static and sufficient.

# ADR-005: Threshold-Based Face Matching

## Status

Accepted

## Context

Face matching requires a decision boundary to determine if a captured face matches a known student.

## Decision

Use **cosine distance threshold** (0.3542) for face matching instead of ML classifier.

## Rationale

- Simpler to implement and debug.
- Threshold can be calibrated empirically (REQ-EMBEDDING-001).
- Lower computational overhead — suitable for offline kiosk.
- Threshold-based approach is standard in face recognition systems.

## Calibration

Threshold calibrated on 30-student dataset (150+ photos). Achieves FAR=0.6%, FRR=2.1%. See `docs/EMBEDDING_CALIBRATION_REPORT.md`.
